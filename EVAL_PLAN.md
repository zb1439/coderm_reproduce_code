## 1. What the experiment is

For each benchmark we already have:
- **100 candidate solutions** per task generated by each of {llama3-8b, gemma-3-4b, ministral-3b, qwen3-8b}
- **Ground-truth pass/fail labels** for every candidate

We want to measure **best-of-N accuracy** using **reward-model-generated unit tests** to do the selection:

```
for task t:
    sols    = 100 candidate solutions (from a solution-generator model)
    uts     = K unit tests generated by a "reward model" for task t
    score_i = number of uts that solution_i passes
    winner  = argmax_i score_i   (ties broken deterministically)
    correct = ground_truth_label[winner]   # is the winner an actually-passing solution?
accuracy = mean(correct across tasks)
```

The "reward model" / "test-case generator" is the thing we're sweeping across
the leftmost column of the table. Each row is a different reward model
checkpoint (`ckpt 4`, `exp 8`, `utrl reward`, `cure reward`, etc.).

Baseline rows for comparison:
- `1-shot (llm direct generate)` — no voting, take the first (or random) solution; numbers shown are from the paper
- `coderm` — numbers reported by the CodeRM paper using their trained 8B UT generator

**Solution schema** (grouped): each line is `{"task_id": str, "solutions": [str, ...]}` with exactly 100 solutions.

**Label schema**:
- HumanEval+/MBPP+: `evalplus` format — `{"eval": {task_id: [{"task_id", "solution", "base_status", "plus_status", ...}, ...]}}`. Use `plus_status == "pass"` as ground truth.
- LCB: `{task_id: [[bool, ...], [bool, ...], ...]}` — one inner list per solution, each is the per-test-case pass/fail vector. Ground truth = `all(results)` (all tests passed).

Both are **100 entries per task, one per solution, in the same order as the solutions list**.

## 3. What the downstream agent needs to do per row of the spreadsheet

One row = one reward-model checkpoint. The agent should:

### Step 1 — Generate unit tests with the reward model

For each task in each benchmark, prompt the reward model to produce unit tests.
CodeRM uses `K = 100` UTs per task with prompts in:
- `/Users/xinyuan/code/coderm/data/benchmark/input_humaneval+_ut.jsonl`
- `/Users/xinyuan/code/coderm/data/benchmark/input_mbpp+_ut.jsonl`
- `/Users/xinyuan/code/coderm/data/benchmark/input_livecodebench_ut.jsonl`

Output format should mirror the paper's `ut_<model>_100.jsonl`: one line per task, `{"task_id", "unit_tests": [str, ...]}`.

### Step 2 — Score each candidate solution against the UTs

Per task:
```python
for sol in solutions:            # 100 solutions
    for ut in unit_tests:         # K unit tests
        run sol + "\n\n" + ut    # one subprocess under time limit
        if passes: score[sol] += 1
```

Use `evaluation/evaluate.py` as a starting point — it already does
`save_sol_and_ut_comb` + `run_unit_tests`. For our files you need
`--sol_path <our sol file> --ut_path <your generated ut file>`.

For LCB use `_func_converted.jsonl` (standalone functions) so that
`sol + "\n\n" + ut` compiles.

### Step 3 — Pick winner and measure accuracy

Per task:
- `winner = argmax(score)` (break ties by lower index / deterministic)
- `is_correct = ground_truth_label[winner]` (look up in the Label file from §2)

Dataset-level metric: `accuracy = mean(is_correct)`.

Fill each cell of the spreadsheet with this number (as a percent).

## 4. Sanity checks before filling numbers

1. **Counts line up**: each solution file has `N_tasks × 100` solutions, each label file has `N_tasks × 100` entries, and the task_ids match 1-to-1 between them. Run:
   ```python
   assert len(solutions[task]) == len(labels[task]) == 100
   ```
   for every task in every benchmark × solution-model file.

2. **Oracle pass@100 sanity check**: for each (benchmark, solution-model), compute "fraction of tasks where ≥1 of the 100 solutions passes". This is the upper bound that ANY best-of-N method can hit. If your reward-model row reports higher than this, something is wrong.

   Current oracle pass@100 from our data:
   | Benchmark | gemma-3-4b | ministral-3b | qwen3-8b |
   |---|---|---|---|
   | HumanEval+ | 78.7% | 94.5% | 84.1% |
   | MBPP+ | 78.0% | 81.0% | 74.9% |
   | LCB v4 | pending | pending | 55.4% |

3. **1-shot baseline re-verify**: take solution index 0 per task, check correctness via label. Should roughly match the "1-shot" row already filled in (`53.6`, `49.2`, `11.98`). If it doesn't match, your label-lookup is wrong.

## 5. What's known about each solution model (for interpreting results)

- **gemma-3-4b** (`google/gemma-3-4b-it`, OpenRouter): solid, concise code
- **ministral-3b** (`mistralai/ministral-3b-2512`, OpenRouter): verbose (2-3× length), has a bias toward snake_case function names even when the problem uses camelCase → lower individual-solution pass rate in MBPP+ with non-standard names, still competitive on pass@100
- **qwen3-8b** (`qwen/qwen3-8b`, OpenRouter): ran with `/no_think` to disable reasoning mode (otherwise fills max_tokens with reasoning and never emits code). Concise output, strong on LCB

All three were generated through `inference/inference_api.py` with `max_tokens=4096`, `temperature=0.6`, `top_p=0.95`, `n=1` per request.
